# Mobi.E Data Processing Pipeline & Storage Optimization
## 1. The Goal
The raw Mobi.E extraction runs every 5 minutes, generating ~1GB of CSV snapshots per day (3.8MB each). To ensure long-term storage efficiency and fast analytics, this pipeline converts 5-minute "Snapshots" into relational "Events" (Charging Sessions and Downtimes). It then compresses the raw data into tiny daily archives.
## 2. Architecture & Scripts
### A. The Extractor (Already Active)
- **Script:** `src/stealth/mobie_label_extraction_cron.py`
- **Role:** Downloads the raw 3.8MB CSV snapshot every 5 minutes via cron to `data/production/mobie_labels/`.
### B. The Processor & State Cache (To be created)
- **Script:** `src/stealth/process_mobie_labels.py`
- **Role:** Runs once daily (e.g., at 02:00 AM via cron) to process the previous day's 288 CSVs.
- **Key Operations:**
  1. **Column Filtering:** Strips out heavy text columns, keeping only: `ID`, `UID DA TOMADA`, `POTÊNCIA DA TOMADA (KW)`, `ESTADO DA TOMADA`, and `ÚLTIMA ATUALIZAÇÃO`.
  2. **Event Detection:** Compares minute-by-minute states to detect when a socket goes `Em uso` (Session Start) and `Disponível` (Session End).
  3. **The State Cache:** Uses a local JSON file (`src/stealth/socket_state_cache.json`) to "remember" sockets that are still charging at 23:55. This solves the Cross-Boundary problem, ensuring sessions that span across midnights are not lost when daily files are deleted.
  4. **Analytics Calculation:** Computes total `Duration` and applies a custom Data Formula (TBD) using the `POTÊNCIA DA TOMADA (KW)` to estimate total `kWh` consumed.
  5. **Storage Cleanup:** Zips the filtered daily data into an archive folder structure (e.g., `data/production/mobie_archive/2026/04/`) and permanently deletes the massive 3.8MB raw files, reducing storage costs by ~98%.
### C. The Database Synchronizer (To be created)
- **Script:** `src/5_db_sync/push_mobie_events.py`
- **Role:** Takes the finalized events generated by the Processor and pushes them to the central Supabase database.
- **Schema Strategy:** Uses a **single unified table** (e.g., `charging_sessions`) rather than a table per month. This avoids database bloat and allows for instant, seamless queries across months and years (e.g., `SELECT * WHERE month = 'April'`).
